# Progressive learner onboarding and customization

## Purpose and boundaries

Build enough understanding of the learner to make concrete teaching decisions, then refine it through actual study. This is separate from mandatory theory-file onboarding: a detailed profile cannot replace readable course theory, and complete theory does not tell you the learner's goals or preferred explanations.

The skill's ELI5 clarity standard is already active for every learner. Onboard the useful depth, pacing, representation, and level of assistance, rather than asking whether explanations should be understandable. Keep stated preferences and claimed background separate from demonstrated ability. Increasing proficiency changes scaffolding and challenge; it does not turn intuitive clarity off.

Reuse the current conversation, supplied profile, checkpoint, and actual attempts before asking questions. Keep intake concise and proportionate to what the learner wants; a few high-impact questions often suffice, but there is no fixed output or question-count limit when a richer intake is requested. When the learner has already supplied a choice, apply it rather than asking it again. Use available native selection/form controls when genuinely supported and helpful, with a free-text alternative; plain-text questions are equally valid. Do not require identity, age, institution, grades, diagnoses, or personal background. Ask only task-relevant constraints or access needs, described functionally, when they affect delivery.

Optional profile questions may be deferred or declined. Once sources are ready and the current objective is clear, start useful tutoring with explicit provisional defaults rather than withholding teaching until every field is filled. For a one-off question, infer the minimum appropriate settings from the request and do not launch a full intake. Personalization is deeper evidence and better decisions over time, not a longer mandatory form.

## Stage 1 — Understand the task and constraints

First identify from existing context:

- Course/topic, current exercise or desired starting point, and available theory/problems.
- Desired outcome: understand a concept, recover prerequisites, solve exercises independently, prepare for an exam, or explain/prove ideas deeply. Specify the agreed scope and what success looks like.
- Deadline and usable study time **if relevant and supplied**; permitted methods, exam format/rubric, calculator/software rules, or instructor notation **if known**. Do not invent dates, assume all exams are written, or demand a syllabus for a narrow question.

If these are materially unclear, one compact round can ask:

1. What course/topic and result do you want to work toward?
2. Is there a deadline, session time limit, or exam requirement that should shape the plan?
3. Which theory file and problem/current location should we use?

Omit any question already answered. Request a missing theory file explicitly; you may collect profile information while waiting, but do not start mathematical teaching before the source gate is met.

## Stage 2 — Learn how to explain and interact

Use stated preferences first. For an ongoing session, establish the few missing choices most likely to change the next response:

| Area | Useful information | Concrete effect |
|---|---|---|
| Language and notation | Requested language, bilingual terms if wanted, source notation | Response language, first-use term explanations, labels; preserve mathematical meaning |
| Explanation depth | Which step is hard, useful past explanations, compact versus detailed preference | Expose the hidden step; reduce familiar background; choose number of conceptual layers |
| Representation | A helpful numerical example, graph, table, algebraic derivation, analogy; display constraints | Select a visual that also fits the mathematics; provide readable alternatives |
| Interaction | Guided attempts, hint size, when full examples help, tolerance for check questions | One meaningful task, appropriate help boundary, direct explanation when stuck |
| Practice and pacing | Fast coverage versus focused practice, time per session, repetitions to avoid | Prioritize A/B/C, useful variants and weak prerequisites rather than duplicate arithmetic |
| Feedback and review | Direct correction, locating the first error, desired summary/checkpoint timing | Targeted repair, review cadence, and concise progress updates |
| Practical access needs | Plain text, larger labels, low-bandwidth/static media, assistive reading needs if volunteered | Choose a usable format without demanding medical details |
| Activities and media | Requested quizzes, fill-ins, graphs, images, native interactions, or mixed output; actual supported capabilities | Choose and combine useful formats instead of imposing the same response layout; use readable fallback only when needed |

An appropriate preference question asks for a useful example: "What made an explanation click before: small numbers, a graph, or seeing the algebra unpacked?" Allow free text; the learner need not select a permanent category. Offer an initial teaching setting when no preference is known: plain language, useful labeled illustrations, formulas with conditions, and guided practice. Adapt the amount and form to the task instead of fixing an example count. This is a revisable default, not an observation about the learner.

Do not infer a fixed "visual/auditory learner" type, intelligence, motivation, or inability from a preference or one error. A chosen visual must still suit the concept. Do not assume one successful analogy works for every subject.

## Stage 3 — Separate background from demonstrated ability

Invite existing work or ask which prerequisites feel secure or difficult **only when this affects placement**. Label this as self-report until the reasoning is checked. Prefer one authentic task over a lengthy diagnostic battery. It can serve both normal practice and placement; record exactly what it tested and whether help was given.

- Stated "I know derivatives" is not a verified level for limits, proofs, or integration.
- A supplied worked attempt may establish some operations and reveal a precise prerequisite gap.
- Watching a worked example or saying "I understand" establishes neither independent solving nor delayed recall.
- Preserve uncertainty as `?`; verify level 4/5 using the evidence rules in the session-state reference.

Do not turn preference onboarding into a hidden exam. Tell the learner when a task is being used to check placement or recall, and honor a request to postpone it while recording the unverified state.

## Stage 4 — Turn the profile into a teaching plan

After the relevant intake, summarize in a few sentences:

1. The immediate goal and course source.
2. The explanation/visual/interaction choices you will actually use.
3. The first topic/task and what remains provisional or unverified.

Invite correction naturally and begin when the source gate is satisfied; no ceremonial approval is needed. A full profile table belongs at requested review/save/transfer, not before every equation.

Translate preferences into behavior. For example, "small examples, fast coverage, explicit exam writing" means introduce an unfamiliar idea with a small labeled example, connect it to the source formula and exam conditions, then assign one decisive step and skip proven pure repetition. It does not mean dumping a full solution, omitting cases, or lowering the evidence standard for mastery.

Keep a stable profile distinct from temporary overrides:

- A current request such as "no quiz in this reply" takes precedence for that reply; preserve the default guided-practice setting afterward unless the learner changes it permanently.
- A new explicit lasting preference replaces the previous preference; record what changed and retain unaffected goals/evidence.
- If deadline and mastery goals conflict, propose a feasible priority order and record what is deferred. Do not promise full mastery from available time alone.
- A course switch retains applicable presentation preferences but rechecks theory, exam constraints, and subject-specific competence.

## Stage 5 — Adapt during learning

Treat statements and observations differently:

- **Explicit preference:** "I want a sign table"; apply it where relevant.
- **Observed response:** "The learner corrected the sign after a labeled table"; record the event and its scope.
- **Provisional hypothesis:** "Labeling positions may help with this type of error"; test lightly rather than turning it into a universal trait.

When the learner says an explanation failed, identify the obstacle and change representation or granularity before repeating the same wording. Ask one targeted clarification only if the obstacle remains unclear. When they solve and justify a technique independently, reduce scaffolding for that technique while preserving review and untested cases. Do not permanently increase explanation depth because of one arithmetic slip.

Record the specific adaptation that helped, with the technique and evidence: for example, "explaining the reference group with counts resolved this denominator confusion" rather than "weak at probability" or "always needs elementary explanations." A request for concision or formal proof changes presentation, not the obligation to keep the decisive reasoning understandable.

At natural milestones, note which approach helped and update the profile when it affects future decisions. Avoid repeated satisfaction surveys and unnecessary introspection questions. Learner requests can change the profile at any time, without resetting progress. Feedback can refine presentation, but competence levels still require actual mathematical evidence.

## Portable learner profile template

Fill only supported facts, marking unknown, self-reported, or provisional items explicitly. Use anonymous/local labels; a legal name is unnecessary. Keep shared presentation preferences separate from per-course settings and evidence. Dates are optional; do not invent them.

```markdown
# Mathematics Learning Profile
- Revision/updated: [actual update or learning milestone]
- Provenance: [current conversation / learner-provided profile / mixed]
- Language and terminology: [explicit request or provisional default]
- Shared teaching preferences: [depth, representations, step size, interaction]
- Activities/media and host capabilities: [explicit preferences, supported formats actually checked, alternatives if needed; not a permanent format restriction]
- Feedback and review preferences: [specific actionable choices]
- Practical format/access needs: [volunteered relevant constraints, or not specified]

## Current course
- Course/topic and goal: [agreed scope and observable outcome]
- Deadline/session budget: [supplied facts, or unspecified]
- Exam/method constraints: [source or learner statement, or unverified]
- Course theory: [actual files and verified scope; access must be rechecked]
- Preferred anchors/examples: [learner-stated or observed; scope and limits]
- Background: [self-reported prerequisites and gaps, distinct from tested ability]
- Demonstrated ability: [brief evidence or accessible checkpoint, never inferred from preferences]
- Teaching plan now: [concrete choices, next step, and provisional defaults]
- Open questions: [only consequential missing details; optional/deferred marked]

## Updates that matter
| Preference/constraint/hypothesis | Basis and scope | Teaching action | Status |
|---|---|---|---|
| [item] | [explicit statement / observed event / provisional idea] | [observable adaptation] | [active / temporary / superseded / needs checking] |
```

An existing profile need not use this exact format. Preserve its supported facts and avoid asking the learner to convert it. A profile can link to a detailed checkpoint, but a link/path alone does not make the content accessible in another chat.

## Persistence and resumption

Maintain profile and checkpoint separately: the profile describes goals and teaching choices; the checkpoint records sources, location, pending task, evidence, and reviews. Include relevant profile content or a compact snapshot in a handoff so another agent can actually use it. On resumption, apply the profile without repeating answered intake questions, recheck source access, and ask only for a material change or missing dependency.

When the learner requests saving or the workspace explicitly authorizes persistent study records, save a profile outside the skill/repository in the learner's chosen or clearly identified local study location. Otherwise return copyable Markdown, and describe accurately whether a file was written. Do not promise automatic cross-chat/platform memory or publish a filled profile to a shared repository. The reusable skill contains only this blank template and generic workflow.
